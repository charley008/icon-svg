# v1.0.6 性能修复与压测报告

测试日期：2026-11-15（北京时间）。本报告不包含线上地址、凭据或业务数据库。

## 结论与原因

线上只读诊断发现，集中抓取合集页面与 CPU 持续满载、内存快速增长、后续上游 504 在时间上吻合。没有重启前的进程或容器资源快照，因此不能宣称全部线上内存消耗已被精确归属；WSL2 对旧版的隔离测试则复现了相同的失效模式。

Go 服务通常只有一个长期运行的业务进程。每个 HTTP 请求由 goroutine 处理；请求持有的元数据、结果切片、模板缓冲区仍被引用时，GC 不能回收它们。原来的数据库查询没有传入请求 context，客户端超时并不会自动终止排队中的查询。单数据库连接使请求在多个查询阶段间排队，部分请求已经持有完整结果，又等待下一次查询。持续进来的请求增加存活对象，GC 无法解决业务积压。GOMEMLIMIT 是软目标，不能当成硬内存限制或请求取消机制。线程数量较少也不代表 goroutine 或业务对象没有积压。

## 修改清单

| 位置 | 修改与效果 |
| --- | --- |
| `internal/app/public_requests.go` | 请求准入、可取消锁等待、带 context 的查询适配器、公共目录单份元数据缓存和有界合集搜索 API。缓存不含 SVG，也不按任意请求 URL 增长。 |
| `internal/app/http.go` | 公共动态页面及下载请求最多 4 个、SVG 资源独立最多 16 个、后台最多 8 个，超额返回 503 + Retry-After；公共请求期限 15 秒；目录页面使用共享快照，详情和 SVG 查询传递取消信号。静态文件和健康检查不占公共名额。索引发布持有写锁时快速返回 503。 |
| `internal/app/store.go` | 公共分组及合集读取支持 context，数据库连接排队和正在执行的查询可被取消。缓存通过 total_changes/data_version 检测变更，并设置最长一分钟刷新期限。 |
| `web/templates/home.html`、`web/static/site.js` | 初始侧栏最多 30 个合集，保留选中项；250 ms 防抖搜索最多返回 30 项，取消过期请求；无 JavaScript 时可按 Enter 进入完整合集总览。 |
| `internal/app/archive.go`、`internal/app/library.go` | ZIP 同时最多一个；公开打包使用可取消的只读事务，下载统计等待写锁和事务时响应取消。 |
| `internal/app/library.go`、`internal/app/library_scan.go` | 冷启动跳过重复探测；提前按合集分组 SVG，去掉每个合集遍历全体文件的二重循环。保留外部修改检查、SVG 校验和文件事务保护。 |
| `internal/app/navigation.go` | 模板导航的数据库读取设一秒期限。 |
| Dockerfile、Compose | 默认 GOMEMLIMIT 从 32MiB 改为 128MiB；没有新增线上 CPU 硬限制。 |
| 发布流程 | 版本号 1.0.6；发布说明从版本文档读取，避免沿用旧版文案。 |

目录缓存只共享不可变快照；过滤和排序结果属于当前请求。SQL 变更后下次请求检查计数并重建；已有请求可完成它获取的旧快照。连接复用异常由一分钟上限兜底。图库原文件、索引和账号数据格式不变。

## 测试环境与步骤

- Windows 11 本机的 WSL2 Ubuntu 24.04，Docker 29.8.1。
- 两版均用 Linux Go 1.26.3 编译，固定 GOMAXPROCS=1。
- 同样限制 1 CPU、512 MiB 内存、无容器交换空间、128 个进程/线程；限制只用于隔离测试和公平比较。
- 使用仓库素材副本，不使用或修改生产文件；定时扫描关闭，以隔离 HTTP 请求行为。
- 每 250 ms 从 cgroup v2 读取 memory.current、匿名内存和累计 CPU 时间，同时记录线程数量。
- 每版依次进行：启动至健康；16 个串行不同合集请求；300 个不同合集请求，以 25 请求/秒发起、客户端 250 ms 超时后关闭连接；30 次恢复探测；32 并发持续 20 秒；10 秒空闲与最终健康检查。
- 持续阶段客户端超时为 2 秒，每轮间隔 20 ms。旧版持续阶段是在前一轮已失效的状态下测试，不能将两版该阶段的吞吐直接视为干净启动时的容量比较。

## 主对比结果

| 指标 | 1.0.5 / 32MiB | 1.0.6 / 128MiB |
| --- | ---: | ---: |
| 启动至健康 | 8.606 s | 3.616 s |
| 普通合集响应中位数 | 260.73 ms | 7.37 ms |
| 普通合集平均 HTML 大小 | 1,022,537 B | 135,702 B |
| 300 次短超时抓取 | 全部超时 | 全部 200 |
| 短超时抓取成功请求 P95 | 无成功请求 | 12.35 ms |
| 短超时抓取峰值 cgroup 内存 | 509.96 MiB | 114.76 MiB |
| 抓取后健康探测 | 30/30 超时 | 30/30 成功，P95 1.19 ms |
| 后续 32 并发阶段 | 320 次全部超时 | 2,549 个 200、21 个 503、1 个 404 |
| 持续阶段峰值 cgroup 内存 | 512.00 MiB | 121.36 MiB |
| 持续阶段峰值匿名内存 | 502.69 MiB | 76.68 MiB |
| 最后空闲阶段 CPU 时间增量 | 11.767 CPU 秒 | 0.000 CPU 秒 |
| 最终健康检查 | 超时 | 200，约 1.44 ms |
| 被 OOM 杀死 | 否 | 否 |

持续阶段的一个 404 来自样本从素材目录中挑选了不可公开的合集，不属于服务器 500 错误。503 为应用的明确过载拒绝，不被计作成功。cgroup 内存包含文件缓存等，并不等于 Go 堆或 Docker stats 扣除缓存后的显示值。旧版触及内存上限时未被 OOM 杀死，仍陷于内存压力和请求积压，印证不能靠等待 OOM 自动恢复。

## GC 参数交叉验证

同样的 300 次短超时抓取，使用旧版提高 GC 目标、新版保持旧 GC 目标，验证改善来源。

| 组合 | 抓取结果 | 随后 15 次健康检查 | 峰值 cgroup 内存 |
| --- | --- | --- | ---: |
| 旧版 + 128MiB | 300 次全部超时 | 15 次全部超时 | 512.00 MiB |
| 新版 + 32MiB | 300 次全部 200 | 15 次全部成功 | 88.74 MiB |

代码修复是主要改善来源，提高 GC 目标本身无法修复旧版。128MiB 为默认素材规模提供扫描和并发时的余量；其余部署应按实际规模调整。服务无分配时不会因为设了 128MiB 就持续占 CPU。

最终候选在加入独立 SVG 请求名额和扫描读取计数修正后，再次以 128MiB 运行同样的 300 次抓取：300 次全部 200，随后 15 次健康检查全部成功，峰值 cgroup 内存 105.05 MiB。

## 发布与部署

发布镜像为 `charley008/icon-svg:1.0.6`，同时更新 `latest`；发布流程验证测试、容器启动/重启、空目录初始化，再构建 amd64/arm64 镜像和素材包。线上 VPS 本次没有压测、重启或自动升级。

部署时保留原有 data、library，先备份，再明确使用 1.0.6 镜像。旧 Compose 或 .env 若显式指定 GOMEMLIMIT=32MiB，新镜像不会覆盖该环境变量；新版在 32MiB 交叉测试也通过，可单独评估是否改到 128MiB。不要把容器硬内存上限直接设为 128MiB。

观察成功请求延迟、503 数量、内存是否在压力停止后稳定，以及健康检查。出现 503 说明工作被拒绝，不能只看低 CPU 就认定容量足够。负载持续很高时，仍建议在 nginx 对动态页面设置总体并发保护、合适的缓存及更完整的耗时日志，并为所有日志配置轮转；这些线上配置本次未改动。

## 限制

本次为单机、短时 HTTP 复现实验，未验证数小时/数日运行、真实公网 TLS/HTTP2、nginx、多租户服务或所有恶意请求模式。CPU 满载本身在持续压测中是正常现象，关键区别是处理完成的请求数、内存是否有界以及停止压力后是否恢复。测试不能证明 VPS 从未被入侵，也不能替代生产的进程级历史监控。
